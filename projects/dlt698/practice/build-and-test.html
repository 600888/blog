    #构建与测试

    #构建

    cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release --parallel
ctest --test-dir build -C Release --output-on-failure
cmake --install build --config Release --prefix ./build/stage

    只需要 C++17、CMake 3.20+ 和匹配的编译器，不依赖 Python。所有构建树都在 build/ 下，build/core 用独立 C++ 入口，build/shared 编共享库，CI 默认用 build/。

    #构建选项

    选项默认说明
    DLT698_BUILD_TRANSPORTON关闭后不编译 Asio TCP / 串口
    BUILD_SHARED_LIBSON单一共享库；设为 OFF 构建静态库
    DLT698_WARNINGS_AS_ERRORSOFF严格警告检查
    DLT698_BUILD_EXAMPLESON构建示例程序

    DLT698_BUILD_TRANSPORT=OFF 的价值见 传输层：关掉之后内存通道、SerialLinkChannel、会话、同步/异步服务全部照常，只少了真实 socket。

    这对测试和交叉编译都有实际意义——受限的 CI 容器、离线开发机、精简的嵌入式环境都能跑测试。

    #测试组织：目录即架构

    测试基于 Catch2（third/Catch2 的 amalgamated 发行版），按被测层次分子目录，每个目录生成一个可执行文件：

    目录CTest 名称覆盖内容
    cpp/tests/commoncommonResult / Error、字节视图与读写游标、ManualExecutor 虚拟时钟
    cpp/tests/codeccodecData 编解码与资源限制、RSD / RCSD / MS 记录描述符
    cpp/tests/protocol/linkprotocol_link帧编解码、CRC、流式拆帧、分片与重组
    cpp/tests/protocol/apduprotocol_apdu统一 APDU 路由、连接服务、GET 家族、SET / ACTION、分块、时间标签
    cpp/tests/serviceservice对象目录与 provider、标准对象与记录、客户端 / 服务器服务、同步封装
    cpp/tests/servicedevice标准数据发布、自定义定义、预算及并发快照
    cpp/tests/sessionsession状态机、事务匹配、取消与超时、诊断回调
    cpp/tests/transporttransport内存通道、串行链路适配
    cpp/tests/transporttransport_tcpTCP 通道与 IO 运行时
    cpp/tests/appapp托管两端、多连接、读写 / 记录、登录、超时、取消与回调析构

    测试目录和模块目录一一对应，这不是巧合。它意味着：

    1. 新增一层时，测试该放哪没有选择余地
    2. 测试边界和模块边界天然对齐，不会出现一个大测试文件什么都测
    3. 某层测试失败时，问题范围立刻锁定在那一层

    #最重要的一条：预期字节不来自被测代码

    这是我在整个项目里认为最关键的一条测试原则。

    协议库有个致命陷阱：如果预期值由被测编码器自己生成，那编码器错了测试也会「通过」。

    // 危险的做法
auto encoded = encode_data(value);
auto decoded = decode_data(encoded);
CHECK(decoded.value() == value);      // 编码错了也发现不了

    dlt698 的做法是独立规范向量——tests/vectors/ 里存放按标准手工推导的字节序列：

    // 正确：断言编码结果等于标准推导的字节
CHECK(encode_data(value) == Bytes{ /* 手工按规约推导 */ });

    这比任何覆盖率数字都重要。覆盖率 100% 的编码器，如果预期值是它自己生成的，可能每一个字节都是错的，而测试全绿。

    手工推导慢、繁琐，而且可能一开始推错——但推错的过程本身就是一次人工校验，能暴露对规约理解上的偏差。

    #一个真实的例子

    用 dlt698_decode 验证一帧：

    dlt698_decode "68 17 00 43 05 07 09 19 05 16 20 00 15 60 05 01 01 40 01 02 00 00 C6 07 16"

    这串字节来自规约示例，不来自本库的编码器。

    #测试辅助

    公用辅助集中在 cpp/tests/catch/test_support.hpp：

    辅助用途
    hex()十六进制字符串与字节互转
    fixture()常用测试装置
    require_ok()断言 Result 成功并返回值
    require_error()断言 Result 失败
    require_truncation_rejected()断言截断输入被拒绝
    CHECK_DECODE_ERROR断言解码返回指定错误码

    require_truncation_rejected() 值得单独说。协议解析器最常见的缺陷就是接受了不该接受的不完整输入——正常路径测试全绿，畸形报文一进来就栈溢出或者读到越界内存。

    这个辅助函数让「截断输入必须被拒绝」变成可以一条断言表达的事情。

    #筛选运行

    ctest --test-dir build -R codec --output-on-failure        # 按测试名
./build/bin/dlt698_test_protocol_apdu "[apdu][get]"       # 按 Catch2 标签

    Catch2 的标签让细粒度筛选成为可能。改了 get.hpp 只想验证 GET 相关测试，不需要跑整个 protocol_apdu 可执行文件。

    #network 标签

    transport_tcp 和 app 默认参与 CTest，但带 network 标签，需要真实回环 socket。

    ctest --test-dir build -L network --output-on-failure

    这样区分是因为这两个测试依赖真实 socket。在受限环境（容器、无回环支持）里可以单独排除：

    ctest --test-dir build -L '~network' --output-on-failure   # 排除网络测试

    其余八个测试全部跑在 MemoryChannel 上，不需要任何 I/O。

    受限环境不能联网时应记录未执行范围——这是 CI 的诚实性要求。不跑测试和跑了测试通过，是两种不同的状态，不能混为一谈。

    #确定性来自哪里

    测试不 flaky，靠的是三个设计：

    设计消除了什么不确定性
    ManualExecutor 虚拟时钟超时、心跳、重发的真实时间依赖
    MemoryChannel网络传输、延迟、丢包
    独立规范向量预期值与被测代码耦合

    有了这三个，测试可以在任意机器上以任意顺序重复运行，结果完全一致。

    #包消费测试

    cpp/tests/package_consumer 是一个独立的包消费测试，配合 package_test.cmake.in 模板，用于验证发布包能被外部项目正确消费。

    这个测试存在的理由是：库自己构建成功，不等于发布包能被消费。发布包里的 CMake 配置、头文件目录结构、导入库位置，任何一处出错都会让使用者在接入时才发现问题——而那时已经发布出去了。
