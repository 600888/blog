    #项目概览

    DL/T 698.45 — 2017

    DL/T 698.45 是国内电力终端通信的通用规约，规定了集中器与采集终端之间的报文格式、交互流程和对象模型。市面上的实现大多以 SDK 形式绑定某一家厂商的芯片，协议细节藏在闭源二进制里，现场联调遇到问题时只能靠猜。

    dlt698 的目标很直接：把协议本身写清楚，写成一个可以读、可以改、可以调试的库。

    • 源码：github.com/600888/dlt698
    • 在线接口文档：600888.github.io/dlt698
    • 面向对象：集中器、采集终端、电力网关的协议对接场景

    #为什么从零写一个

    现场做规约对接时，真实痛点不是「报文发不出去」，而是：

    痛点现象dlt698 的做法
    调试不可见只有抓包，不知道库里为什么没解出来每层都有可读的编解码入口，能单独喂一帧字节看结果
    行为不可预期分包、半包、粘包由厂商实现决定流解析、分帧、重组都是有状态机、有边界检查的显式逻辑
    依赖不可控必须绑定特定 SDK 和芯片平台纯 C++17 + CMake，-DDLT698_BUILD_TRANSPORT=OFF 可完全不碰网络
    无法自测想验证一段逻辑必须连真实设备MemoryChannel 让整条协议栈跑在内存里，无需硬件

    换句话说，它同时是一个可用的库，也是一个可读的实现。这个区别在写代码时决定了大量的设计取舍。

    #技术选型

    #C++17，不绑定平台

    选 C++17 而不是 C++20，是因为需要支持较老的编译器链（含 MSVC 和 ARM64 交叉编译的 GCC）。用到的特性只有 std::variant、std::optional、结构化绑定这些，C++17 已经足够。

    网络和串口用 Asio，但只作为可选依赖。关掉 DLT698_BUILD_TRANSPORT 之后，内存通道、会话、同步服务、编解码全部照常可用——这让整个库能在没有网络栈的嵌入式环境里跑测试。

    #单一库目标，多个别名

    对外只暴露 dlt698::dlt698 一个 CMake 目标。历史上拆分过的 core / session / service 保留为兼容别名，但不再生成独立库。

    原因很实际：协议实现的头文件天然互相引用，拆成多个库会带来一堆传递依赖和循环依赖的 CMake 处理。合并成单一库反而简单。

    find_package(dlt698 1.0 CONFIG REQUIRED)
target_link_libraries(your_app PRIVATE dlt698::dlt698)

    #每个公开头文件都是文档

    头文件按 .hpp 组织，公开接口全部带中文 Doxygen 注释，说明参数含义、返回值、错误行为、内存所有权、资源限制，以及异步接口的回调和生命周期约定。

    这不是为了好看。规约库最怕的是「用错了但不知道」——比如以为 ByteView 拥有内存，实际它只是借用。这类约定必须写在头文件里，而不是让使用者去翻实现。

    传输TCP 客户端 / 监听 / 双向拨号、原始串口、串行时序适配、内存通道

    #明确不做

    项目状态原因
    广播地址会话行为❌广播不应答，会话模型不适用
    自动重拨号 / 重登录❌属于业务策略，交给应用层决定
    真实 ESAM 安全验收⚠️需要厂商 SDK、模块型号和测试凭据
    RS-485 硬件时序⚠️逻辑已实现，真实排空驱动待实测

    其中安全层的设计值得一提：库只定义 security::backend.hpp 这份适配合约，实际的认证、MAC、加解密交给厂商 SDK 后端，库内不保存任何明文密钥。这不是偷懒，是安全模块该有的边界划分。

    指标数量
    源码文件234 个（C++ 与 Python 合计）
    代码行数约 39,400 行
    公开头文件41 个，按 9 个命名空间分层
    标准 OI 常量132 个
    单元测试可执行文件10 个，按被测层次分目录
    预编译发布包10 个（Linux / Windows / macOS × 静态 / 动态）

    十个测试可执行文件的划分本身就是一张架构地图——每个目录对应一层，测试边界和模块边界对齐：

    测试目录对应层覆盖重点
    tests/common基础设施Result / Error、字节读写游标、虚拟时钟
    tests/codec编解码Data 资源限制、RSD / RCSD / MS 描述符
    tests/protocol/link链路帧编解码、CRC、流式拆帧、分片重组
    tests/protocol/apdu应用协议APDU 路由、GET 家族、SET / ACTION、分块
    tests/service对象服务对象目录、标准对象、记录、快照
    tests/session会话状态机、事务匹配、取消与超时
    tests/transport传输内存通道、串口链路适配、TCP 与 IO 运行时
    tests/app托管层两端配对、多连接、回调析构

    #一个细节：预期字节不来自被测代码

    协议库的测试有个致命陷阱：如果预期值由被测编码器自己生成，那编码器错了测试也会「通过」。

    dlt698 的处理方式是独立规范向量——tests/vectors/ 里存放按标准手工推导的字节序列，测试直接断言编码结果与之相等。这条约束比任何覆盖率数字都重要。
